# 3.02 동작 명세

> 작성 전

`run <taskId>` 한 번이 어떤 순서로 무엇을 하는가.

## 담을 내용

- [ ] 실행 순서 — 카드 읽기 · 검증 → 실행 가능 판정(계획 승인 · 작업 순서 포함) → 모델 선택 → claim 커밋 → worktree → 스폰 · 대기 → 실제치 기록 → 브랜치 상태 판정 → 회수
- [ ] 계획 승인 확인 — claim 전에 main HEAD에서 닿는 커밋 중 제목이 정확히 `Plan-Approved: <ID>`이고 유효한 서명이며 서명자가 `humanSigners`에 있는 커밋을 찾는다. 없으면 claim하지 않고 실행 가능 판정에서 뺀다. worktree는 claim 커밋에서 갈라지므로 승인 커밋은 태스크 브랜치에서도 닿는다. 판정 기준은 최상위 ADR-022 · 2.02 구현 계획 형식, 구현은 별도 카드
- [ ] 작업 순서 확인 — 실행할 카드가 `backlog/work-order.md`의 현재 단계(앞 단계가 전부 Done)에 있고 파일이 최신일 때만 claim한다. 같은 단계의 카드는 병렬 대상이지만 동시성 허가(기본 1)가 실제 동시 실행 수를 정한다 (최상위 ADR-023 · BL-016 · RAIL-023, 구현은 별도 카드)
- [ ] 단계별 커밋 — claim 커밋(main)과 실제치 기록 커밋(태스크 브랜치)은 그 카드 파일만 넣고 push하지 않는다. claim 전에 커밋되지 않은 `backlog/` 변경이 있으면 claim하지 않는다 (최상위 ADR-023 · RAIL-021, claude-code-agile-hooks TASK-59)
- [ ] 실패 경로 — 타임아웃, 비정상 종료, 카드 형식 오류, worktree 미커밋 변경, 계획 승인 없음 · 서명 무효 · 사람이 아닌 서명자(사유를 나눠 남김), 낡은 작업 순서 파일, 토큰 계량 값 없음(`TBD(최상위 Q-18)`)
- [ ] 회수 — 자손 스냅샷 → SIGTERM → 유예 → SIGKILL, Registry 제거, 허가 반납
- [ ] 시퀀스 다이어그램(mermaid)
