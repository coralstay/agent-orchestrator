# 0. 문서 정보

이 문서는 Sigkill Foundry의 실행 기반 컴포넌트 agent-orchestrator의 설계 문서다. 스펙 주도 개발(SDD)을
따른다 — 구현은 이 명세에서 도출하고, 명세와 코드가 어긋나면 명세를 먼저 고친 뒤 코드를 맞춘다.

## 상위 문서

이 문서의 상위 문서는 최상위 Sigkill Foundry 설계 문서다. agent-orchestrator는 그 3.03 컴포넌트 명세 §1에
정의된 컴포넌트이고, 최상위 요구사항 ORC-001 ~ ORC-031을 구현한다.

| 상위 | 이 문서에서의 쓰임 |
| --- | --- |
| 최상위 1.02 원칙 | 이 문서의 원칙(1.02)은 최상위 원칙을 상속한다. 최상위 원칙에 어긋나는 원칙 · 요구사항은 둘 수 없다 |
| 최상위 2.03 기능 요구사항(ORC) | 이 문서의 요구사항(2.03)은 같은 ID로 이어받는다 |
| 최상위 3.03 §1 | 이 문서의 3.01 · 3.03은 그 컴포넌트 표를 패키지 · 클래스로 내린다 |
| 최상위 3.05 설계 결정 | 이 문서의 결정(3.05)은 최상위 ADR을 어기지 않는다. 어겨야 하면 최상위 결정을 먼저 고친다 |

이 문서 안에서 "최상위"를 붙이지 않은 원칙 `Pn` · 목표 `G-n` · 미결 사항 `Q-n` · 장 번호는 이 문서의 것이다. 최상위 문서의 것은
"최상위"를 붙여 적는다 (예: 최상위 P2, 최상위 3.03 §1, 최상위 Q-16).

## 문서 구성

설계 문서는 다섯 문서로 이어진다. 문서마다 하나의 질문에 답하고, 앞 문서의 답이 뒤 문서의 입력이 된다.

| 번호 | 문서 | 답하는 질문 |
| --- | --- | --- |
| 1 | 프로젝트 제안서 | 왜 만들고, 무엇을 어디까지 하는가 |
| 2 | 요구사항 명세서 | 무엇을 만족해야 하는가 |
| 3 | 아키텍처 설계서 | 어떻게 구성되고 동작하는가 |
| 4 | 구현 계획서 | 어떤 순서로 만들고, 무엇으로 판정하는가 |
| 5 | 구현 결과 보고서 | 무엇을 만들었고, 판정은 어떻게 나왔는가 |

장은 `문서 번호.장 번호`로 가리킨다 (예: 3.05 설계 결정). 장 안의 절은 `§`로 가리킨다 (예: 3.03 §1).

## 규범 용어

| 표현 | 뜻 |
| --- | --- |
| 반드시 ~한다 (MUST) | 어기면 명세 위반이다 |
| ~해야 한다 (SHOULD) | 어길 때는 이유를 3.05 설계 결정에 남긴다 |
| ~할 수 있다 (MAY) | 선택 사항이다 |

## 요구사항 표기

- 목표는 `G-<번호>`로 식별하고 1.03 목표와 범위에 둔다. 이 문서의 목표는 자신이 이바지하는 최상위 `G-n`을 적는다.
- 요구사항 접두어는 최상위 2.03과 같은 `ORC`다. 번호 공간은 최상위 문서 하나다.
  - 최상위 `ORC-nnn`은 같은 ID로 이 문서의 2.03에 이어받는다. 같은 ID는 같은 요구사항이다.
  - 하위 번호(`ORC-nnn.m`)나 이 저장소 전용 번호 대역은 두지 않는다. 최상위 요구사항을 더 잘게 나눠야 하면 최상위 2.03에서 새 번호로 쪼갠다.
  - 최상위 요구사항에 닿지 않는 새 요구사항은 최상위 2.03에 먼저 올려 번호를 받는다. 번호는 재사용하지 않는다.
- 품질 요구사항은 최상위 `NFR-nnn`을 같은 방식으로 이어받아 2.04에 둔다.
- 모든 요구사항은 수용 기준을 하나 이상 가진다(4.02).
- 아직 정하지 않은 값은 `TBD(Q-n)`으로 적고, `Q-n`을 4.03 미결 사항에 둔다. 최상위 미결 사항에 걸린 값은 `TBD(최상위 Q-n)`으로 적는다.
- 설계 결정은 이 저장소의 backlog 결정(`decision-N`)이 원본이고, 3.05가 그것을 정리한다.

## 추적 규칙

모든 요구사항은 다음 사슬로 앞뒤가 이어진다. 사슬이 끊긴 항목은 둘 수 없다.

1. 최상위 요구사항 `ORC-nnn` (최상위 2.03) — 최상위 목표 `G-n`에 이어진다.
2. → 이 문서의 요구사항 `ORC-nnn` · `ORC-nnn.m` (2.03 · 2.04)
3. → 컴포넌트 · 인터페이스 (3.03 · 3.04) — 컴포넌트 명세는 자신이 구현하는 요구사항 ID를 적는다.
4. → 수용 기준 (4.02) · backlog 태스크 (4.01) — 요구사항 하나는 이 저장소 backlog 태스크(`AO-n`)의 AC로 내려간다. 태스크 카드는 자신이 구현하는 요구사항 ID를 적는다.
5. → 테스트 — 테스트는 `@DisplayName`에 `<카드 ID>#<n>`(AC) · `<카드 ID>#B<k>`(카드의 비즈니스 규칙) 표식을 단다. AC 하나씩 TDD로 쓰고 훅이 강제한다 (decision-13).
6. → 결과 판정 (5.02) — 수용 기준마다 통과/실패와 그 증거(테스트 로그 · 실측)를 남긴다.

- 원칙(1.02)에 어긋나는 요구사항은 둘 수 없다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.
- 계획과 다르게 구현한 것은 5.03 계획 대비 편차에 적고, 해당 설계 결정(3.05)에 연결한다.
- 이 저장소의 결정이 최상위 요구사항 · 설계와 어긋나면, 어긋남을 3.05에 남기고 최상위 문서의 해당 장을 고칠 대상으로 올린다.

## 편집 규칙

- 설계 내용의 원본은 저장소의 `design/**/*.md` 하나다. 다른 곳(Claude 앱 문서 · 위키 등)에 사본이나 편집 원본을 두지 않는다. 고칠 때는 이 파일을 직접 고치고(Claude Code · GitHub 편집기) 커밋 · PR로 남긴다. 최상위 Sigkill Foundry도 같은 규칙이다.
- 한 장 = 한 문서. 같은 내용을 두 장에서 고치고 있다면 한쪽을 장 참조 한 줄로 접는다.
- 최상위 문서에 있는 내용은 옮겨 적지 않고 "최상위 n.nn"으로 가리킨다. 이 문서에는 이 저장소에만 있는 것(패키지 · 클래스 · 결정 · 테스트)을 쓴다.
- 다이어그램 원본은 `design/diagrams/*.dot`이다. DOT으로 먼저 쓰고, DOT으로 표현할 수 없는 것(시퀀스 등)만 mermaid(`.mmd`)로 쓴다.
- `design/build-diagrams.py`가 원본을 `design/diagrams/<이름>.svg`로 렌더한다. 색은 원본에 센티넬 hex로 적고, 빌드가 SVG 안의 CSS 변수(라이트 기본 · 다크 재정의)로 바꾼다. 빌드 전제: graphviz(`dot`), mermaid 렌더용 `npx` + 로컬 Chrome.
- 생성된 SVG는 손으로 고치지 않는다. 원본을 고치고 빌드를 다시 돌려 같은 커밋에 넣는다. 장 사본은 `![설명](../diagrams/<이름>.svg)`로 참조한다.
- 저장소 Markdown의 외부 링크는 문서 맨 아래 링크 정의 블록에 모으고, 본문은 `[표시][키]`로만 쓴다.
