# 1.01 배경과 문제

agent-orchestrator는 Sigkill Foundry의 실행 기반 컴포넌트다 — 태스크마다 역할 에이전트를 독립 프로세스로 띄우고, 정책을 바깥에서 주입받아 모델을 고르고, 끝나면 프로세스째 죽여 회수한다 (최상위 3.03 §1).

## Sigkill Foundry 안의 자리

Sigkill Foundry는 소프트웨어 태스크를 backlog.md 계층으로 나누고, 태스크마다 역할형 Claude Code 에이전트를
독립된 `claude -p` 프로세스로 띄웠다가 태스크가 끝나면 죽여서 회수하는 소프트웨어 공장이다(최상위 1.01).
그 안에서 프로세스를 띄우고 죽이는 일을 맡는 것이 agent-orchestrator다. 나머지 일은 각자의 컴포넌트에 있다.

| 컴포넌트 | 층 | agent-orchestrator와의 관계 |
| --- | --- | --- |
| **agent-orchestrator** | 실행 기반 | 태스크 판독 · 실행 가능 판정 · 모델 선택 · worktree · 스폰 · 회수 · 기록 |
| claude-code-agile-hooks | 규율 | 에이전트 세션 안의 절차(task view 필독 · In Progress · AC마다 커밋 · 커밋 전 테스트 · Done)를 강제한다. agent-orchestrator는 그 절차를 다시 구현하지 않는다 |
| coding-agent-git-commit-tool | 계측 | 커밋마다 `Tokens-Used` 등 트레일러를 남긴다. agent-orchestrator는 트레일러를 읽기만 한다 |
| backlog.md | 상태 | 태스크 카드의 상태 · 의존 · AC를 담는다. agent-orchestrator는 CLI로 읽고 고친다 |
| 대상 프로젝트 | 판정 규칙 | 테스트 명령의 종료 코드가 판정이다. agent-orchestrator는 내용을 판정하지 않는다 |

의존은 한 방향이다. agent-orchestrator가 backlog.md · git · 에이전트 프로세스를 부르고, 에이전트는
agent-orchestrator를 부르지 않는다 (최상위 3.01).

## 무엇을 하는가

진입점은 `orchestrator run <taskId>` 하나이고, 태스크 하나를 처리하고 결과를 남긴 뒤 끝난다 (decision-2).
한 번의 실행은 다음 순서를 따른다.

| # | 단계 | 하는 일 | 근거 |
| --- | --- | --- | --- |
| 1 | 카드 읽기 · 검증 | 카드를 읽고 Description의 `### Token Budget` 소절에서 `estimated`를 찾는다. 없거나 형식이 틀리면 실행하지 않고 사유를 남긴다 | decision-6 |
| 2 | 실행 가능 판정 | `status = To Do`이고 직접 의존이 전부 Done인 카드만 실행한다. `In Progress` + 사람 담당은 사람 락이다 | decision-9, 최상위 ORC-005 |
| 3 | 모델 선택 | 예상 `in+out`으로 정책 파일에서 모델을 고른다 | decision-10 |
| 4 | claim | main의 카드를 `In Progress` + 담당자 `@claude`로 바꿔 커밋한다 | decision-9 |
| 5 | worktree | claim 커밋을 기준으로 `../<repo>-wt/<id>` worktree와 `task/<id>` 브랜치를 만든다 | decision-3, 최상위 ORC-012 |
| 6 | 스폰 · 대기 | worktree 안에서 Implementer를 `claude -p` 프로세스로 띄우고 제한 시간까지 기다린다 | decision-7, 최상위 ORC-001 · ORC-024 |
| 7 | 실제치 기록 | 커밋 트레일러 합계(`commits`)와 헤드리스 JSON 세션 총량(`session`)을 카드에 `attempt n` 또는 `actual`로 남긴다 | decision-5 · decision-8 |
| 8 | 회수 | 프로세스와 자손을 종료하고, 세션을 Registry에서 지우고, 동시성 허가를 반납한다 | 최상위 ORC-003 · ORC-004 |

## 문제

agent-orchestrator가 없으면 아래 문제들이 사람 손이나 에이전트의 자발성에 남는다.

| 문제 | 왜 문제인가 | agent-orchestrator의 답 |
| --- | --- | --- |
| 컨텍스트 경계를 누가 긋는가 | Sigkill Foundry에서 컨텍스트 경계는 프로세스 경계다(최상위 P2). 세션 안에서 단계만 나누면 이력이 공유된다 | 역할마다 별도 `claude -p` 프로세스를 띄운다. 프롬프트는 argv 원소 하나로 넘기고 stdin은 닫는다 |
| 끝난 세션을 어떻게 지우는가 | 헤드리스 세션에는 `/clear`를 보낼 단계가 없다. 프로세스 종료가 곧 컨텍스트 폐기다(최상위 P3) | 회수 = 자손 포함 프로세스 종료 + Registry 제거 + 허가 반납. 여러 번 불러도 허가를 이중 반납하지 않는다 |
| 자손 프로세스가 남는다 | 부모가 먼저 죽으면 자손이 init으로 재부모화되어 더는 찾을 수 없다 | 부모를 죽이기 전에 자손 목록을 떠 두고 SIGTERM → 유예 → SIGKILL 순으로 끝낸다 |
| 사람과 에이전트가 같은 카드를 잡는다 | backlog.md의 `isReady`는 `In Progress`도 참으로 본다(1.51.0 실측). 사람이 잡은 카드에 에이전트가 붙을 수 있다 | `status = To Do`를 직접 판정하고, 실행 직전 claim 커밋으로 에이전트 실행분(`@claude`)을 사람 락과 구분한다 |
| 같은 카드를 두 곳에서 고친다 | 카드 파일은 main과 태스크 worktree 양쪽에 있다. 양쪽에서 고치면 병합 충돌이 난다 | claim 이후 카드 변경은 태스크 브랜치에서만 한다 |
| 에이전트끼리 파일이 섞인다 | 태스크 = 파일이라는 계층(최상위 P7)은 에이전트가 물리적으로 갈라져 있어야 성립한다 | 태스크마다 git worktree를 만든다 |
| 토큰을 누가 재는가 | 토큰 수는 모델이 아니라 API 응답 메타데이터다. 오케스트레이터가 재면 측정 도구의 일을 중복한다 | 측정 코드를 두지 않고 커밋 트레일러 계약만 읽는다. 트레일러는 마지막 커밋 뒤의 턴을 빠뜨리므로 세션 총량을 함께 남긴다 |
| 예상 토큰을 어디에 두는가 | backlog.md 1.51.0에는 숫자 필드가 없고, 직접 넣은 frontmatter 키는 다음 `task edit`에서 지워진다(upstream #918) | 카드 Description의 `### Token Budget` 소절에 둔다 |
| 모델을 누가 고르는가 | 모델 선택을 코드에 고정하면 정책을 바꿀 때마다 오케스트레이터를 고쳐야 한다(최상위 ORC-009) | 의존성 없는 설정 파일(`model.upTo.<N>` · `model.default`)로 바깥에서 주입한다 |
| 헤드리스 세션이 규율을 벗어난다 | `--bare`는 훅을 건너뛰어 트레일러와 게이트가 함께 꺼진다. 승인 프롬프트에 답할 사람도 없다 | `--bare` · `--dangerously-skip-permissions`를 쓰지 않고, 묻지 않고 진행하되 검사를 끄지 않는 권한 모드로 띄운다 |

## 하지 않는 것

- 에이전트 안의 절차를 강제하지 않는다 — claude-code-agile-hooks가 한다. agent-orchestrator는 프롬프트로 절차를 지시하고 결과를 브랜치 상태로 본다 (decision-7).
- 에이전트 대신 커밋하지 않는다. 커밋은 에이전트가 AC마다 한다 (decision-7).
- 토큰을 재지 않는다 — coding-agent-git-commit-tool이 남긴 트레일러를 읽는다 (decision-5).
- 작업 결과의 옳고 그름을 판정하지 않는다 — 대상 프로젝트 테스트의 종료 코드가 판정이다 (최상위 P5).
- Claude Code 말고 다른 코딩 에이전트 CLI를 띄우지 않는다. 에이전트 실행부만 `AgentRunner` 포트로 갈라 둔다 (decision-7).
- 보드를 감시하지 않는다. 감시 방식은 최상위에서 미정(`TBD(최상위 Q-10)`)이고, 진입점은 단발 실행이다 (decision-2).
