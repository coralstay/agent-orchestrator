# 1.02 원칙

agent-orchestrator의 모든 요구사항 · 설계가 따라야 하는 불변 규칙이다 — 최상위 원칙을 상속하고, 이 저장소의 결정에서 나온 원칙을 더한다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다.

## 상속하는 최상위 원칙

최상위 1.02의 원칙은 이 저장소에도 그대로 적용된다. 아래는 각 원칙이 agent-orchestrator에서 어디에 닿는지다.

| 최상위 원칙 | 요지 | agent-orchestrator에서의 적용 |
| --- | --- | --- |
| 최상위 P1 | 판단의 독립성 — 판정 역할은 구현 역할의 컨텍스트를 물려받지 않는다 | 역할마다 새 프로세스를 띄우고, 이전 세션의 이력을 넘기지 않는다 |
| 최상위 P2 | 컨텍스트 경계 = 프로세스 경계 | 에이전트는 반드시 별도 `claude -p` 프로세스다. 역할 사이 전달은 커밋 · 카드 · 파일로만 한다 (P3 · P4) |
| 최상위 P3 | 회수는 kill이다 | 회수는 자손 포함 프로세스 종료(SIGTERM → 유예 → SIGKILL) + Registry 제거 + 허가 반납이다. 상시 대기하는 세션을 두지 않는다 |
| 최상위 P4 | 최종 게이트는 하나다 | agent-orchestrator는 게이트를 늘리지 않는다. 판정은 대상 프로젝트 테스트와 브랜치 상태에서 읽는다 |
| 최상위 P5 | 판정기는 유한하고 결정적이다 — 오케스트레이터는 Exit Code만 본다 | 작업 내용을 해석해 판정하지 않는다. 테스트 종료 코드와 브랜치 상태(커밋 · 카드 상태)만 본다 |
| 최상위 P6 | 레일은 규율, 에이전트는 자발성 | 세션 안의 규율은 claude-code-agile-hooks에 맡기고, 그 레일을 끄는 실행 방식을 쓰지 않는다 (P5 · P8) |
| 최상위 P7 | 계층은 코드 단위에 고정된다 — 에이전트 배정 = 파일 | 태스크마다 worktree를 분리한다 (P9). 사람 락은 대상 파일 단위로 본다 |
| 최상위 P8 | 판단 단위는 태스크다 | 모델 · 역할은 카드마다 정책이 정한다. 프로젝트 단위로 고정하지 않는다 |
| 최상위 P9 | 경계선은 측정해서 정한다 | 모델 정책의 내장 기본값은 근거 없는 임시 값으로 표시하고, 실측(`runs.jsonl`)이 쌓이면 다시 정한다. 동시성 상한은 실측 전까지 1이다 |

## 이 저장소의 원칙

| ID | 원칙 | 근거 |
| --- | --- | --- |
| P1 | **런타임 의존성을 두지 않는다.** 언어 · 런타임은 Java 25, 빌드는 Gradle(Kotlin DSL) + wrapper다. 동시성은 virtual thread · `ProcessBuilder` · `Semaphore`만으로, CLI 인자 파싱도 직접 구현한다. 정책은 설정 파일이 아니라 `AllocationPolicy`를 구현한 자바 클래스이고, 교체는 JDK 표준(`-Dpolicy.class` · `ServiceLoader`)만 쓴다. 테스트 의존성(JUnit 5)만 둔다. | decision-1 · decision-12. 대상 프로젝트 게이트가 `gradlew test` 종료 코드를 전제하므로 같은 도구로 맞추면 검증 경로가 하나다. 최상위 ADR-002(Java 25 + virtual thread + Semaphore)를 따른다 |
| P2 | **테스트가 먼저다 — AC 하나씩 TDD.** 카드 안에서 AC #n의 테스트(실패) → 최소 구현 → 정리 → 커밋 → AC #n+1 순으로 간다. 테스트는 AC와 카드의 비즈니스 규칙(설명의 `## 비즈니스 규칙` 절, `- B<k> (AC #<n>) …`)을 함께 다루고, `@DisplayName`에 `<카드 ID>#<n>` · `<카드 ID>#B<k>` 표식을 단다. 별도 테스트 카드 · 시그니처 스텁 + `@Tag("pending")`은 새로 만들지 않는다. | decision-13(decision-11 대체). claude-code-agile-hooks의 `require_test_first.py`가 강제한다(최상위 RAIL-019 · ADR-020) — `.claude-code-agile-hooks.json`의 `testFirst`로 켠다. 이미 있는 pending 테스트 · 스텁은 해당 구현 카드가 정리하고, `pendingTest` 태스크는 그때까지 둔다 |
| P3 | **Claude Code 전용, 실행부만 포트로.** 구현하는 에이전트는 Claude Code 하나다. 에이전트를 띄우고 기다려 결과를 받는 부분만 `AgentRunner` 포트로 가른다. 헤드리스 JSON 파싱은 Claude 구현 안에만 둔다. | decision-7 · decision-8. 제품마다 권한 모델 · 출력 형식 · 토큰 보고 · 커밋 방식이 달라, 지원 제품이 늘수록 보장할 수 있는 것이 "띄우고 결과를 받는다"로 줄어든다 |
| P4 | **에이전트 대신 일하지 않는다.** 에이전트 안의 절차는 claude-code-agile-hooks가 강제하고, agent-orchestrator는 프롬프트로 지시하고 결과를 브랜치 상태로 판정한다. 코드 커밋은 에이전트가 AC마다 한다. | decision-7, 최상위 P5 · P6. agent-orchestrator가 직접 하는 커밋은 claim과 실제치 기록뿐이고, 둘 다 단계별 커밋 규칙을 따라 그 카드 파일만 넣는다 (P7, 최상위 ADR-023). 계획 승인 커밋은 사람만 만든다 (최상위 ADR-022) |
| P5 | **측정하지 않고 읽는다.** 토큰은 토큰 계량 컴포넌트(이름 미정)가 잰 결과만 읽는다. 그 컴포넌트의 이름 · 저장소 · 측정 방식과 읽는 계약은 `TBD(최상위 Q-18)`이다. 특정 측정 도구의 코드 · 설치 방식에 의존하지 않는다. 측정 실패가 보고되면 재측정 · 추정하지 않고 사유를 그대로 남긴다. coding-agent-git-commit-tool은 포맷 레이어라 토큰 트레일러를 남기지 않는다. | 최상위 ADR-021 · ORC-021. 토큰 수는 API 응답 메타데이터라 측정 도구의 일이다. decision-5(커밋 트레일러 `Tokens-Used`만 읽는다)는 최상위 ADR-021과 어긋나 대체할 결정이 필요하다(3.05) |
| P6 | **토큰은 한 단위, 두 출처.** 단위는 `in=N out=M`(입력은 캐시 쓰기 · 읽기 포함)이고 예상치도 같은 형식이다. 실제치는 토큰 계량 컴포넌트의 값과 `session`(헤드리스 JSON `usage` 합계)을 병기한다. 정책 판단은 `session` 기준이다. 계량 값의 단위 · 귀속 단위(커밋 · 세션)는 `TBD(최상위 Q-18)`이다. | decision-8. decision-8의 `commits`(트레일러 합계)는 출처인 `Tokens-Used` 트레일러가 없어져(최상위 ADR-021) 계량 컴포넌트의 출력으로 바뀌어야 한다 — 대체 결정이 필요하다(3.05). 트레일러 합계가 마지막 커밋 뒤의 턴을 빠뜨린다는 스파이크 결과(입력 약 26% 누락)는 귀속 단위를 정할 때의 근거로 남긴다 |
| P7 | **카드의 값은 본문에, 변경은 claim 뒤 태스크 브랜치에서.** 예상 · 실제 토큰은 카드 Description의 `### Token Budget` 소절에 둔다. 실행 직전 main의 카드를 `In Progress` + `@claude`로 claim 커밋하고, 그 뒤의 카드 변경(AC 체크 · Done · Token Budget)은 태스크 브랜치에서만 한다. claim은 사람의 계획 승인 커밋(`Plan-Approved: <ID>`, 서명자가 `humanSigners`)이 있는 카드에만 한다 — 승인이 없으면 실행 가능 판정에서 뺀다. 카드 접근은 `TaskCardSource` 포트 뒤에 둔다. | decision-6 · decision-9. backlog.md 1.51.0의 frontmatter 키는 편집 때 지워진다(upstream #918). 양쪽에서 같은 카드를 고치면 병합 충돌이 난다. claim 커밋을 원격 main에 그대로 실으려면 PR은 merge commit으로 병합한다. 승인 게이트는 최상위 ADR-022 · BL-017이고, 오케스트레이터의 claim은 에이전트 세션 밖이라 훅의 게이트가 돌지 않으므로 같은 기준을 직접 지켜야 한다(구현은 별도 카드) |
| P8 | **레일을 끄는 실행 방식을 쓰지 않는다.** 에이전트는 `--bare` · `--dangerously-skip-permissions` 없이 띄운다. 헤드리스 세션은 원격에 push하지 못하게 막는다(`--disallowedTools "Bash(git push:*)"`). | decision-5 · decision-7, `AgentSpawner` · `AgentRunner.ClaudeCodeRunner` javadoc. bare 모드는 훅을 건너뛰어 트레일러와 게이트가 함께 꺼진다 — 최상위 ORC-002 |
| P9 | **태스크 하나에 worktree 하나.** 태스크마다 `../<repo>-wt/<id>`와 `task/<id>` 브랜치를 만들고, 같은 태스크를 두 번 동시에 돌리지 않는다. 미커밋 변경이 남은 worktree는 강제로 지우지 않고 사람이 판단하게 남긴다. | decision-3, 최상위 P7 · ORC-012. 브랜치명은 커밋 트레일러의 `Task-Id` 추출 규칙과 claude-code-agile-hooks의 브랜치 확인을 함께 만족한다 |
| P10 | **진입은 단발 실행이다.** 진입점은 `orchestrator run <taskId>` 하나이고, 태스크 하나를 처리하고 기록한 뒤 끝난다. 감시 루프를 붙일 때는 같은 실행 흐름을 재사용한다. | decision-2. 보드 감시 방식은 최상위에서 미정(`TBD(최상위 Q-10)`)이고, 단발 실행만으로 스폰 · 회수 · 기록을 검증할 수 있다 |

## 최상위 요구사항과의 관계

이 저장소의 원칙 중 P3은 최상위 문서보다 좁고, P5 · P6 · P7의 근거 결정(decision-5 · decision-8 · decision-9)은 최상위 ADR-021 · ADR-022 · ADR-023보다 먼저 정해져 어긋난다. 어긋남은 3.05 설계 결정에 남기고 최상위 문서를 고칠 대상으로 올린다 (0 문서 정보 추적 규칙). P1은 최상위와 맞는다.

| 원칙 | 최상위 | 관계 |
| --- | --- | --- |
| P3 (Claude Code 전용) | 최상위 ORC-023 — 역할 하나를 다른 프로바이더 CLI로 띄울 수 있다(MAY), 최상위 3.03 §1 Agent Spawner | ORC-023은 MAY라 위반은 아니다. 다른 프로바이더는 `AgentRunner` 포트의 다른 구현 자리로만 남는다 |
| P5 · P6 (측정하지 않고 읽는다, 두 출처) | 최상위 ADR-021 · ORC-021 — 토큰 계량은 별도 토큰 계량 컴포넌트(이름 미정)가 맡고, coding-agent-git-commit-tool은 포맷만 맞춘다. 측정 방식은 `TBD(최상위 Q-18)` | 원칙은 최상위에 맞췄다. 근거 결정 decision-5(`Tokens-Used` 트레일러만 읽는다) · decision-8(`commits` = 트레일러 합계)은 어긋난 채 남아 있어 대체 결정이 필요하다 |
| P7 (claim) | 최상위 ADR-022 · BL-017 — 계획 → 리뷰 → 계획 승인 뒤에만 `In Progress`. 최상위 ADR-023 · BL-016 · RAIL-023 — 착수 커밋은 그 카드 파일만, 실행 순서는 작업 순서 파일(`backlog/work-order.md`, 같은 단계 = 병렬)을 따른다 | 원칙은 최상위에 맞췄다. decision-9는 claim 전 승인 · 작업 순서 확인을 적지 않아 보완 결정이 필요하다. 현재 코드(`BacklogClient.isRunnable`)는 둘 다 보지 않는다 — 구현은 별도 카드 |
| P1 (런타임 의존성 없음) | 최상위 ORC-010 — 정책은 `AllocationPolicy`를 구현한 자바 클래스로 쓰고 `-Dpolicy.class` → `ServiceLoader` 순으로 고른다. 정책 미지정 · 로딩 실패면 에러 메시지와 함께 시작하지 않고(폴백 없음), 고른 정책 클래스와 경로를 기록한다. 외부 라이브러리는 쓰지 않는다 | 맞는다. 둘 다 JDK 표준이라 P1을 지킨다 (decision-12, decision-10을 대체). 현재 코드는 decision-10 기준 `ModelPolicy` 스텁이고 `AllocationPolicy` 구현은 DRAFT-4가 맡는다 |
